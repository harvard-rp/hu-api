# Character archives and reopening

An archived refusal keeps the sheet, character ID, use state, reviews, House references and lifetime refusal count. The archive is excluded from current lists, slot usage and campus eligibility. Every threshold refusal records `archivedCharacter: true` in review history. Earlier reviews and annotations remain visible to the owner.

| Method and path                                                  | Success | Authorization and result                                                                                                                                                          |
| ---------------------------------------------------------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/v1/characters/archives`                                | 200     | Owner's archive summaries. Read the sheet and reviews through the existing owned routes.                                                                                          |
| `GET /api/v1/characters/{characterId}/reopening-requests`        | 200     | Owner's request timeline, including prior archive cycles.                                                                                                                         |
| `POST /api/v1/characters/{characterId}/reopening-requests`       | 201     | Owner submits `requestId`, `expectedRevision` and `reason`. The client generates a UUID and keeps it with the attempted operation.                                                |
| `GET /api/v1/staff/characters/archives`                          | 200     | `characters.reopen` grants paginated archive summaries with the pending request ID, if any. Uses `limit` and `after` like the review queue.                                       |
| `GET /api/v1/staff/characters/{characterId}/archive`             | 200     | `characters.reopen` grants the archived sheet and its reviews.                                                                                                                    |
| `GET /api/v1/staff/characters/{characterId}/reopening-requests`  | 200     | `characters.reopen` grants the reopening timeline. Previously reopened drafts can expose their request timeline to reopening staff. Their current draft content stays owner-only. |
| `POST /api/v1/staff/characters/{characterId}/reopening-requests` | 200     | A non-owner with `characters.reopen` resolves the pending request using `requestId`, the current `expectedRevision`, `decision` (`accepted` or `declined`) and `justification`.   |

Reasons and justifications must be nonblank and at most 2,000 characters. The timeline projects only request ID, requested revision, reason and timestamp, optional decision and justification, decided timestamp and resulting revision. Internal actor IDs are available to trusted database audit only. The sheet is unchanged when a request is filed or declined. An accepted request creates a new draft revision of the same character, consumes one slot and retains suspension and history. Any later refusal archives again. Each subsequent reopening requires a new pending request and staff acceptance. A decline permits a new request under a fresh ID without a cooldown.

A request can be made while full. It reserves no slot. Acceptance at capacity returns `409 CHARACTER_CAPACITY_REACHED` and leaves the request pending. A duplicate, resolved or competing request can return `409 CHARACTER_REOPENING_CONFLICT`, a stale revision returns `409 CHARACTER_REVISION_CONFLICT`, and a mismatched owner or a character outside the operation's state returns `404 CHARACTER_NOT_FOUND`. A missing capability returns `403 CHARACTER_REOPENING_FORBIDDEN`. If the result is uncertain, read the timeline and current sheet before deciding to retry. A successful mutation is never repeated by a replay.

The same checks apply in the authenticated `public.character_reopening` PostgREST facade. Writes serialize on player capacity, then take the eligible character row lock when needed. Pending uniqueness is enforced for each archive review, and request IDs are unique across cycles. Decisions record the authenticated actor, reason and time. Reviewers require an independent grant to reopen and cannot decide their own requests. PostgreSQL rechecks session and capability after lock waits before committing any mutation. This workflow leaves the Discord server and delivery unchanged.
